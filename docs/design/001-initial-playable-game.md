# Дизайн: первая играбельная версия The True Path

## Цель и пользовательский опыт

Игрок сразу видит весь небольшой лабиринт сверху, героя, светящийся выход и короткую подсказку по управлению. Задача понятна без отдельного меню: провести героя от стартовой клетки к выходу. Стены явно отличаются от проходов, допустимый ход плавно перемещает героя на соседнюю клетку, а попытка пройти сквозь стену даёт короткую визуальную и звуковую реакцию.

После достижения выхода движение прекращается, появляется сообщение о победе и предложение начать заново. Полный игровой цикл занимает примерно 1–3 минуты при первом прохождении и не требует перезагрузки страницы.

## Правила и состояния

### Игровое поле

- Лабиринт состоит из сетки `17 × 9` клеток по `32 × 32` логических пикселя.
- Внешняя граница закрыта стенами. Карта содержит ровно одну стартовую клетку `S` и ровно один выход `E`.
- Между `S` и `E` существует маршрут. Кратчайший маршрут должен включать не менее 24 перемещений, а карта — не менее трёх тупиков, чтобы восприниматься как лабиринт.
- Герой занимает одну клетку. Перемещение возможно только по четырём ортогональным направлениям и только в проходимую соседнюю клетку.
- Диагональное движение, толкание объектов, враги, ловушки и проигрыш в первой версии отсутствуют.

### Состояния игры

1. `playing` — игра принимает команды движения и перезапуска.
2. `moving` — визуальная анимация допустимого хода длится `0.12` секунды; новые команды движения временно игнорируются.
3. `won` — герой находится на выходе, движение отключено, показан экран победы; команда перезапуска доступна.

Состояние `moving` является кратким состоянием контроллера представления. Авторитетная позиция в модели меняется один раз при принятии хода. Победа создаётся один раз при первом допустимом входе на `E` и показывается после завершения анимации.

### Перезапуск

Клавиша `R` доступна в любом состоянии. Она отменяет текущую анимацию, возвращает модель и спрайт героя на `S`, сбрасывает счётчики временных событий, скрывает победный экран и переводит игру в `playing`.

## Сценарии

### Основной сценарий

1. HTML5-страница загружается, canvas получает изображение игры, а состояние становится `playing`.
2. Игрок читает цель `REACH THE LIGHT` и подсказку `WASD / ARROWS · R RESTART`.
3. Нажатие направления в свободную соседнюю клетку запускает плавное поклеточное движение.
4. Игрок исследует развилки и тупики; стены не позволяют покинуть проходы или границы карты.
5. Герой входит на клетку выхода, её свечение усиливается и появляется сообщение `PATH FOUND`.
6. Игрок нажимает `R`, после чего начинается чистая новая попытка с исходной позиции.

### Альтернативные и ошибочные сценарии

- Нажатие в стену оставляет позицию неизменной, кратко смещает героя на 2 пикселя к стене и возвращает назад, воспроизводит тихий звук блокировки.
- Второе направление во время `0.12`-секундного перемещения игнорируется; очередь команд не создаётся.
- Одновременные направления обрабатываются по фактическому порядку событий: первый принятый ход блокирует остальные до конца анимации.
- Удержание клавиши не создаёт специального автоповтора игры; учитываются события `pressed`, которые предоставляет браузер и Defold. Для точного прохождения игрок может нажимать клавиши по одной.
- После победы направления игнорируются и не создают повторное событие победы.
- Потеря фокуса страницы не сохраняет внутреннее состояние удерживаемой клавиши. После возврата фокуса следующее новое нажатие работает обычно.
- Изменение размера окна сохраняет всё поле видимым; вокруг области `16:9` допустимы поля.
- Если ресурс не загрузился или возникла JavaScript-ошибка, браузерная проверка завершается ошибкой, а релиз не считается готовым.

## Техническая реализация в Defold

### Версия и конфигурация

- Закрепить стабильный Defold/Bob `1.13.1` в корневом файле `.defold-version`.
- Использовать Java 25 для Bob согласно актуальному руководству Defold.
- `game.project` задаёт имя `The True Path`, bootstrap `/main/main.collectionc`, логическое разрешение `640 × 360`, HTML5 scale mode `Fit`, WebAssembly streaming и ввод из `/input/game.input_bindingc`.
- Использовать `wasm-web`. Потоковый `wasm_pthread-web` не нужен, поэтому требования cross-origin isolation отсутствуют.
- Использовать стандартный render pipeline Defold и одну ортографическую камеру в режиме `Auto Fit`; пользовательский render script не нужен.

`main.collection` содержит четыре объектных роли:

- `game` — tilemap-компонент и `game.script`, владеющий текущей сессией;
- `player` — sprite-компонент без собственной игровой логики;
- `camera` — ортографическая камера, направленная на центр `640 × 360`;
- `hud` — GUI-компонент с подсказкой и победным overlay.

### Данные лабиринта

`game/maze.lua` содержит единственное авторитетное описание карты как массива строк одинаковой длины:

- `#` — стена;
- `.` — пол;
- `S` — проходимый пол и старт;
- `E` — проходимый пол и выход.

Модуль разбирает карту в неизменяемую структуру и предоставляет операции получения размеров, поиска старта и выхода, проверки проходимости и проверки инвариантов. Валидация отклоняет неизвестные символы, неодинаковую длину строк, открытую внешнюю границу, несколько `S`/`E` и недостижимый выход.

Tilemap `game.tilesource` содержит плитки пола, стены и выхода. При `init()` контроллер заполняет слой `maze` через `tilemap.set_tile()` по тем же данным `maze.lua`; отдельной копии карты в `.tilemap` нет.

Координаты карты считаются от левого верхнего угла, начиная с 1. Для мира используется начало поля `(48, 16)`, а строка карты при отображении инвертируется по Y. Центр клетки вычисляется только общей функцией преобразования, чтобы модель, tilemap и герой не расходились.

### Чистая модель состояния

`game/game_state.lua` не вызывает Defold API и владеет:

- ссылкой на валидированную карту;
- текущими координатами героя;
- статусом `playing` или `won`;
- числом принятых, заблокированных и победных событий.

Основные операции: создать состояние, попытаться сделать ход, получить снимок состояния и сбросить состояние. Попытка хода возвращает структурированный результат `moved`, `blocked` или `won`. После первого `won` последующие команды движения ничего не меняют, а счётчик побед остаётся равен 1.

### Состояние и сообщения

`main/game.script` является единственным engine-facing владельцем сессии:

- в `init()` валидирует лабиринт, создаёт модель, заполняет tilemap, ставит героя на `S`, получает input focus и сообщает GUI состояние `playing`;
- в `on_input()` переводит actions в вызовы модели, управляет блокировкой ввода и перезапуском;
- при допустимом ходе запускает `go.animate()` позиции `player` на `0.12` секунды с мягким ease-out;
- при блокировке запускает короткую возвратную анимацию и звук `blocked` без изменения модели;
- после завершения победного хода отправляет `show_victory` в `/hud#gui` и воспроизводит `victory`;
- в `final()` освобождает input focus и снимает window listener.

GUI принимает только сообщения `show_playing` и `show_victory`. Он не владеет правилами игры. Сообщения не содержат произвольный пользовательский текст.

Для браузерной проверки HTML5-сборка публикует через `html5.run()` небольшой read-only снимок в `window.__THE_TRUE_PATH_STATE__`: `status`, координаты героя, `blocked_count` и `win_count`. Значения формируются только из чисел и фиксированных внутренних строк. В нативной/headless-сборке этот вызов пропускается.

### Ввод, движение и столкновения

`input/game.input_binding` связывает:

- `W` и стрелку вверх с `move_up`;
- `S` и стрелку вниз с `move_down`;
- `A` и стрелку влево с `move_left`;
- `D` и стрелку вправо с `move_right`;
- `R` с `restart`.

Обрабатывается `action.pressed`. Сенсорное управление и экранный D-pad в первую версию не входят. Физические collision objects не используются: проходимость целиком определяется сеточной моделью до перемещения, поэтому герой не может проникнуть в стену или накопить физическую погрешность.

### Камера, GUI, графика и звук

- Логическая сцена имеет размер `640 × 360`; поле `544 × 288` располагается в координатах от `(48, 16)` до `(592, 304)`.
- Фиксированная камера центрирована в `(320, 180)` и использует `Auto Fit`, поэтому всё поле и GUI остаются видимыми при изменении окна.
- HTML5 canvas использует режим `Fit`, не получает CSS border/padding и располагается по центру страницы на тёмном фоне.
- Визуальный стиль — минималистичный пиксель-арт «ночной каменный лабиринт»: фон `#0B111A`, пол `#172534`, стены `#31485E`, герой `#69E6DF`, выход и победные акценты `#FFD166`, основной текст `#EAF2F8`.
- Стены имеют светлую верхнюю грань, пол — слабую текстуру, герой — простой силуэт путника с бирюзовым свечением, выход — янтарную руну. Руна плавно пульсирует и остаётся узнаваемой без анимации.
- Текст интерфейса первой версии — английский: это исключает добавление внешнего шрифта ради кириллицы. Используются только перечисленные короткие фразы.
- Звук состоит из двух коротких оригинальных WAV-эффектов: приглушённый щелчок блокировки и двухнотный победный сигнал. Фоновая музыка отсутствует. Звук запускается только после пользовательского нажатия, что соответствует ограничениям браузеров.

### HTML5, сборка и GitHub Pages

`scripts/fetch_bob.sh` читает `.defold-version`, скачивает соответствующий `bob.jar` из официального Defold release и сохраняет его в игнорируемый `.tools/`. Скрипт проверяет код ответа и не использует плавающую версию.

`scripts/build_html5.sh` выполняет Bob из корня проекта, создаёт release bundle `wasm-web` в `build/html5`, добавляет `.nojekyll` в фактический каталог приложения и проверяет наличие `index.html`, `.wasm` и игровых архивов.

`scripts/test_headless.sh` создаёт headless bundle с `test/test.settings`, запускает его с ограничением времени и требует финальную строку `TEST {"event":"suite_end","status":"pass",...}`. Тестовый settings-файл меняет bootstrap на `/test/test.collectionc`, не изменяя `game.project`.

`package.json` закрепляет `@playwright/test` как dev dependency. Браузерный тест поднимает локальный HTTP-сервер для `build/html5`, открывает Chromium, собирает ошибки страницы и консоли, отправляет клавиши через обычный input path и проверяет `window.__THE_TRUE_PATH_STATE__`. Фиксированная последовательность решения хранится только в тесте и обновляется вместе с утверждённой картой.

`.github/workflows/pages.yml`:

- на pull request запускает headless tests, release HTML5 build и Playwright smoke test без публикации;
- на push в `main` и при `workflow_dispatch` выполняет те же проверки, загружает только статический bundle через `actions/upload-pages-artifact` и публикует отдельным job через `actions/deploy-pages`;
- использует Java 25, Node LTS, `contents: read`, а `pages: write` и `id-token: write` выдаёт только deploy job;
- использует environment `github-pages` и сообщает итоговый URL;
- ожидаемый адрес проекта после включения Pages: `https://favoredo.github.io/the-true-path/`.

## Ручной сценарий приёмки

1. Выполнить `./scripts/test_headless.sh` и сохранить итоговую structured result строку.
2. Выполнить `./scripts/build_html5.sh`, затем `./scripts/serve_html5.sh`.
3. Открыть локальный URL, убедиться в отсутствии ошибок консоли и прочитать подсказку управления.
4. Сделать ход в стену и проверить возвратную анимацию и тихий щелчок.
5. Пройти лабиринт штатными клавишами, проверить единственный экран `PATH FOUND` и победный сигнал.
6. Нажать направление после победы — состояние не должно измениться.
7. Нажать `R` — герой и интерфейс должны вернуться в исходное состояние.
8. Повторить smoke test после публикации по `https://favoredo.github.io/the-true-path/`.

## Решения и компромиссы

- Выбрано поклеточное движение вместо непрерывной физики. Оно подчёркивает решение лабиринта, исключает проникновение в стены и позволяет точно воспроизводить тестовые маршруты.
- Выбран один экран без следящей камеры. Полная карта остаётся видимой, а адаптивность сводится к сохранению области `640 × 360`.
- Сенсорное управление отложено. Мобильный viewport проверяется на читаемость, но играть в MVP предполагается с физической клавиатуры.
- Карта хранится в Lua, а tilemap строится из неё при запуске. Это оставляет один источник истины ценой небольшой работы в `init()` для 153 клеток.
- Внешние игровые библиотеки и native extensions не используются. Единственная новая npm-зависимость — закреплённый Playwright для проверок, она не входит в игровой bundle.
- Read-only HTML5 test state остаётся доступным в браузере. Он не содержит секретов и позволяет проверять canvas-игру без хрупкого распознавания пикселей.
- Интерфейс MVP выбран на английском, чтобы не добавлять шрифт только ради нескольких строк. Локализация остаётся отдельным изменением.
- Минимальная оригинальная графика и два коротких эффекта предпочтены внешнему asset pack, чтобы не создавать лицензионных зависимостей.

## Открытые вопросы

Технических блокеров для реализации нет. Решения, на которые стоит обратить внимание при утверждении:

- поклеточное движение с отдельными нажатиями, без встроенного удержания;
- отсутствие сенсорного управления в первой версии;
- английский текст интерфейса;
- выбранная тёмная бирюзово-янтарная пиксельная стилистика;
- read-only test state в HTML5 и Playwright как dev dependency.
